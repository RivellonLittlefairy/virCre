摄像头会话时限修复与断流诊断

2026-10-20。此修复晚于GitHub v0.1.1发布，既有Release资产没有替换。

当前结论：采集永久暂停，之后由用户手动关窗

用户已明确澄清：“相机画面暂停或黑屏，电脑窗口还在”，看到异常后手动关闭投屏窗口。因此下文SC_CLOSE、Controller结束、EOF及exitCode=0是后续手动退出的正常链路，不能据此判断Windows或其他软件自动关闭投屏。此前将“退出”理解成窗口自行消失，导致排查方向偏离，以下按历史过程保留并以本节结论为准。

用户最近几次复现都先出现“请将整个投屏画面移入同一显示器”提示。根因是GetRegion严格要求整个客户区落在单个显示器内，任一边缘越界或跨屏就抛错；供帧循环把所有采集异常转为永久paused，必须用户点击继续，故静置观察时一直停留在暂停画面。日志能证明边界检查失败，尚不能从旧日志还原是哪个边缘或多少像素越界。正常运行600/615秒限制则是另一个已经独立修复的问题。

边界与自动恢复修复

  • 枚举与窗口客户区相交的显示器，在物理桌面坐标中裁切、拼接，再缩放到原有虚拟显示分辨率。支持负坐标、不同屏幕位置；屏幕外和显示器间空隙保持黑色，不拉伸可见区域。
  • 每次GPU复制后重新读取窗口位置，跨入的新显示器在下个帧周期准备；切换显示器或分辨率自动重建对应采集源，离开的屏幕及时释放。只有窗口相交的屏幕会被采集，跨屏的额外资源成本高于单屏，多个屏幕不保证同时采样。
  • 最小化、锁屏、安全桌面、临时COM或显示器变化错误发送暂停心跳，500毫秒后重试。可采集时自动恢复，不设置手动paused标志。用户主动暂停保持原语义，必须主动继续；不支持的平台或未知错误仍给出暂停原因。
  • 保持排除自身窗口、锁屏/安全桌面访问检查、实际相机尺寸和输入协议。composition原始画布限制为32Mi像素以约束大窗口内存；不保存画面。没有删除连接故障检查或拦截正常关闭消息。
  • 新增desktop-capture-recovering和desktop-capture-recovered固定阶段，便于区分等待恢复与用户手动退出。

确认的问题

桌面日志中10:58:52启动、11:08:52数据流结束，相隔约600秒。内嵌的ApplicationCameraSession曾从启动开始安排600秒关闭，并在615秒强杀整个scrcpy服务进程。这是正常使用也会到期退出的代码问题。

另有不足十分钟的EOF记录，部分之前出现最小化或跨显示器采集暂停。暂停与断流的时间相关性不等于因果；目前不能确认这些退出由读超时、网络、系统、用户关窗或其他原因造成。手机现有logcat没有保留对应代理事件。

修改范围

  • 删除正式应用会话的600秒定时关闭。启动时不再建立615秒进程死亡期限，正常会话无时长上限。
  • 退出清理开始后才建立15秒兜底，覆盖scrcpy编码器stop/join和虚拟设备清理卡住；这个期限不是正常使用时限。超时强杀路径不等待日志锁，正常退出由JVM结束守护线程。
  • 独立的历史P0脚本/ShellMain仍保留测试时长参数，不属于正式应用窗口路径。
  • 未删除socket读写超时和渲染失败处理；它们用于检测故障，不应当把健康连接按累计运行时间关闭。短时断流原因仍待用户复现确认。
  • 删除“最多615秒自行退出”的旧错误提示。断连后无法确认远程进程状态时，要求重连再清理。

诊断日志

本机日志：%LOCALAPPDATA%\virCre\logs\desktop.jsonl，超过256KiB后轮换到desktop.jsonl.previous。相机阶段附带从本次桌面会话准备开始计算的单调时长elapsedMs。每种阶段只记录一次；没有新增图像、输入文字、剪贴板或页面内容记录。

阶段含义
phone-input-timeout / eof / io-error / error手机输入连接断开类别；phase为accept、hello、packet、ack之一。
phone-shutdown-started / phone-resources-closed手机已进入退出流程、虚拟设备资源清理结束。强杀可能来不及输出最后记录，不能单凭缺失阶段判断。
scrcpy-exited exitCode=...本机投屏子进程实际退出码；在输出排空后报告。
desktop-close-requested / desktop-pump-ended桌面主动请求关窗，或供帧循环发现窗口结束。
desktop-input-eof / socket-error / session-error桌面输入数据流结束、socket错误或其他会话错误。
desktop-frame-timeout / startup-timeout帧交换超时、启动阶段超时。

继续补充固定来源日志：客户端quit事件、退出快捷键、Windows关闭/系统关闭消息、客户端时间限制及设备断连；主程序向投屏发送关闭请求；服务端Controller或Video处理器先结束。它们只观察现有行为，不吞掉关闭消息、不忽略连接故障，也不改变输入路径。下一次复现仍需用户手动操作。

16:50第二次用户复现：Windows关闭消息先于手机退出

本次运行.cache/camera-exit-preview，16:50:08.051出现跨屏采集暂停。16:50:10.519先收到client-native-system-close（WM_SYSCOMMAND / SC_CLOSE），接着是client-native-close（WM_CLOSE）、client-quit-event，16:50:10.529手机Controller结束，16:50:10.536手机开始清理。直到16:50:10.625桌面才收到EOF，16:50:10.629桌面才请求关闭投屏，最终exitCode=0。该顺序表明本次终止由Windows关闭命令开始，手机退出及EOF是后续结果；桌面主程序的关窗收尾不是最初原因。

此证据不能确定消息由用户、键盘加速键、当前进程内部或其他进程发送，也不能证明是Windows定时策略。用户此前报告静置退出。当前代码没有发现与本次初始SC_CLOSE对应的主动关窗入口，不以猜测归因，也不吞掉合法关闭命令。

下一层日志仅记录关闭相关类别：Alt+F4系统键、标题栏关闭按钮、SC_CLOSE传递方式、是否为前台窗口、最近输入距今的粗粒度区间（1秒内、10秒内、10秒以上、未知）。InSendMessageEx只能区分跨线程发送与本线程/已投递消息，不能确定发送者PID；不记录其他按键、输入文字或鼠标坐标。设置页和启动提示遗留的“每次最长10分钟”文案同步移除。

用户复现方式

  1. 关闭旧版主程序和投屏窗口，运行本次提供的完整预览目录，旧Release包仍带有原定时限制。
  2. 按日常方式打开应用及扫一扫，保持使用。若再次自动关闭，记录大致时间以及当时是否最小化、跨屏、锁屏或网络变化。
