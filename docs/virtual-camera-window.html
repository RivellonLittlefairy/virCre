虚拟摄像头投屏同分辨率预览（实验版）

把电脑投屏窗口客户区盖住的桌面区域作为手机 App 的相机画面，随窗口移动、缩放。不需要图片或手动框选。Windows 端仍由 WGC 采集监视器并裁切；投屏窗口自行排除采集，避免画面递归。

安装器与便携包：out/installers/（0.1）。用户已确认拖动刷新版本可用。本次增加虚拟摄像头设置与可调目标帧率，默认启用，移除右键相机模式入口。只修改源码、编译打包，没有自动操作微信、安装测试APK或执行测试；新设置的交互、保存恢复和帧率效果由用户手动确认。

本次改动

虚拟设备、虚拟相机和桌面输入 socket 现在都由内置 scrcpy 服务端持有。复用 scrcpy 的新显示编码流程，将同一个 VDM 显示的 Surface 直接连接编码器。没有第二块 Android 镜像显示，也不再创建独立的 SurfaceFlinger 输出、手工设置图层栈或投影。

相机注册尺寸、桌面JPEG输入尺寸与scrcpy创建的虚拟显示尺寸统一。新窗口启动时，内置scrcpy在手机上读取主屏的尺寸与DPI，按手机自然方向创建虚拟显示，不再固定为1440×2560、480dpi；手机临时横屏不会把新窗口初始方向也转成横屏。编码器可能做少量像素对齐，相机与桌面输入以实际虚拟显示尺寸为准。电脑上的初始窗口按这个比例适应显示器可用空间，不再强制720×1280。相机最高30fps，PC桌面目标默认15fps，可在设置内调整为1–30fps，手机按相机请求复用最新桌面帧。首帧提交只说明供帧Surface收到了画面，不证明真实App已经读取、显示或成功扫码。

普通独立窗口、相机窗口和桌面快捷方式共用这套参数。读取在打开新窗口时进行，不依赖缓存中的某个固定手机型号，也不为此重扫应用列表；已经打开的窗口保持原尺寸，关闭后重新打开才使用手机最新的屏幕设置。手机主屏信息无法获取时，scrcpy沿用自身的1920×1080、240dpi兼容回退，此时无法保证与手机比例相同。

设置与默认启动方式

进入“设置 → 虚拟摄像头”，通过“打开应用时启用虚拟摄像头”控制新窗口是否采集下层桌面，默认开启。点击打开应用、双击卡片和桌面快捷方式使用相同设置；右键只保留创建快捷方式，不再提供相机模式选项。关闭此开关后，新应用使用普通独立窗口；已经打开的应用保持原模式，重复打开会切回该窗口。要切换已有应用的模式，需先关闭它再重新打开。

“桌面相机目标帧率（fps）”允许1–30的整数，默认15。输入后按回车或移开焦点，或使用增减按钮提交；修改后无需重开相机会话，在后续帧周期生效。输入小数会取整，清空后失焦恢复原值，范围外持久化值恢复15。开关和目标帧率随主题、收藏一起保存在当前用户本地设置；旧版设置文件缺少新字段时使用开启/15fps，显式关闭的值会被保存。

现有实验版同时仅支持一个相机窗口，0.1.2已移除正常运行的600/615秒期限，正常使用不再按时长自动退出。仅在会话已经结束、资源清理卡住时保留15秒进程清理兜底；断连、渲染失败仍可结束会话。需要再打开其他普通窗口时可先关闭全局相机开关，已有相机窗口仍保持原模式。帧率是供帧目标，不代表手机App实际显示或分析帧率；提高目标会增加处理量，不保证达到设置值。0.1.1安装包没有这些修复；见0.1.2更新说明及生命周期修复与断流诊断。

拖动期间持续更新

用户反馈按住标题栏开始拖动就冻结画面。最近一次会话日志没有对应的自动暂停事件；源码确认Windows拖动/缩放会阻塞普通SDL事件循环，原scrcpy只在该循环处理SC_EVENT_NEW_FRAME。手机与PC供帧线程可以继续工作，但新解码帧没有被显示，表现为窗口冻结。

内置SDL3.dll版本为3.4.18，其Windows消息循环已提供模态拖动定时器，并通过SDL_EVENT_WINDOW_EXPOSED（data1=1）通知重绘。现相机模式在该通知的主线程回调中取出最新帧并显示，检查窗口ID、可见状态、断线与手动暂停状态，加入重入保护，模态重绘上限约30fps。沿用SDL现有通知，不添加额外定时线程，不在解码线程调用渲染器。

最新帧缓冲区仍只保留一帧；另用互斥锁保护待处理通知标志，拖动期间不堆积帧通知，普通主循环恢复后允许通知对应的帧已经被消费。模态重绘不根据新帧自动调整窗口大小；销毁时先撤销事件观察器再释放渲染资源。此修复改善显示调度，不改变设置中的PC采集目标。后续边界修复已移除跨屏和部分离屏导致的永久暂停；最小化或锁屏时仍暂停供帧，恢复可采集状态后自动恢复。

源码依据：SDL Windows模态消息循环、SDL_OnWindowLiveResizeUpdate；本项目scrcpy的screen.c事件观察器、帧缓冲和窗口销毁流程。

分辨率、帧率与性能

最初使用640×480 PNG，每帧采集、压缩、传输并收到确认后再等200ms，因此真实更新低于5fps。此前固定720p方案未满足竖屏全画面扫描要求，现以scrcpy实际创建显示的尺寸作为唯一来源：编码器完成尺寸对齐后才注册相同尺寸的相机，通过ready向PC传回尺寸；JPEG编码质量0.88。处理与传输耗时算入1000/目标fps毫秒的周期，默认约66.7ms，而非额外等待。

PC只裁切scrcpy实际显示内容覆盖的下层桌面。窗口变宽或变高后产生的letterbox黑边不纳入相机输入；标题栏和外边框也不纳入。按行复制源裁片，复用裁片缓冲区，由系统图像编码器线性缩放到目标尺寸，不再用托管代码逐像素放大，也不往输出额外加黑边。这是原生图像处理，不代表已经采用GPU或硬件视频编码。

处理量由手机实际分辨率决定。例如1440×2560为3,686,400像素，是1280×720的4倍、640×480的12倍；单张ARGB约14.06MiB，15fps仅一遍解码像素就约210.94MiB/s。JPEG属于有损编码；CPU、内存带宽、网络与手机功耗会上升，实际帧率可能下降。物理采集区域若只有720×1280，放大成1440×2560不会创造新的细节；放大电脑窗口可增加采样像素。字体与二维码边缘的实际效果需手动确认。

每次仅有一帧在处理中，不积压；采集、编码、网络往返或手机解码慢时，实际发送率会下降。可在“运行中 → 相机画面”查看近期手机接收确认的fps和有效载荷Mbps；该数字不是微信最终显示或分析的帧率。USB与稳定局域网通常比延迟较高的无线连接更有利。

当前仍是JPEG逐帧编码、手机Bitmap解码及纹理上传，不保证手机原生分辨率稳定达到15fps。若要兼顾原分辨率与更高帧率，下一步应考虑H.264硬编解码链路。原camera-direct包可作为已确认可用的低画质对照版本。

启动与使用

  1. 正常关闭旧版virCre及应用窗口。安装版从开始菜单启动virCre；便携版完整解压后运行根目录的VirCre.Desktop.exe。单实例转发可能使未关闭旧版时的重复启动继续使用旧进程。保留完整发布目录；通常不需要管理员权限。
  2. 虚拟摄像头需要 Android 16 或以上手机，并保持 ADB 在线。Android 10～15 自动使用普通应用窗口，参见版本兼容说明。应用列表仍使用缓存，需要更新时点击刷新。
  3. 在设置中确认虚拟摄像头已开启、目标帧率合适，然后直接打开应用。若此应用已有普通窗口，先关闭它再重开以采用新模式。
  4. 投屏窗口可靠边、移动到其他显示器或跨屏。手机画面实际盖住的桌面区域会缩放到虚拟显示分辨率（启动时跟随手机屏幕尺寸）；各屏幕部分按物理桌面坐标拼接，屏幕外及屏幕间空隙补黑，不拉伸剩余可见区域。改变Windows窗口大小只改变采样区域与采样细节，不改变Android虚拟显示的像素尺寸。
  5. 手动打开 App 的相机功能；出现 Android 摄像头权限提示时在投屏窗口允许。普通窗口的授权不一定适用于本次虚拟设备。
  6. “运行中 → 相机画面”可以暂停、继续，也会显示手机相机状态：等待应用打开、流已配置、已提交首帧或渲染失败。关闭此应用窗口后停止采集并清理本次会话。

暂停与连接

  • 最小化、完全离开屏幕、Windows锁屏/安全桌面或暂时捕获异常时发送暂停占位画面，返回可采集状态后自动恢复，暂时错误每500毫秒重试。用户手动暂停仍需显式继续；未知的非临时错误保留手动暂停和原因提示。
  • 切换显示器和分辨率时自动重建受影响的采集源；仅保留与窗口相交的屏幕。跨屏会增加GPU读回、CPU复制和内存开销，屏幕间画面不是同步快照。其他窗口若遮挡此区域，也会出现在桌面画面中；Windows可能显示系统采集边框。
  • 暂停每500ms发送心跳。传输超时或断线会结束会话；恢复连接后重试关闭失败条目，再重新打开。不会在断线后自动恢复供帧。
  • 静止桌面可能没有新的 WGC 帧，程序会保留最新监视器像素供移动裁切。若捕获服务静默停止产帧且未通知关闭，可能继续显示旧画面；暂停后继续可重建采集。此边界尚未完成手动验证。
  • 图像只在内存中处理，不保存截图或录像。桌面日志记录固定阶段、错误及暂停原因，不保存画面、输入文字、按键或剪贴板内容。

适用范围与验证边界

  • Android API ≥36、主用户0；当前每次只允许一个虚拟摄像头 App，正常运行没有固定时长上限，清理开始后才启用15秒进程退出兜底。普通窗口保持原有启动与电脑中文输入路径。
  • 相机只属于对应 VDM 内的应用，不替换手机主屏或其他普通窗口中的相机。应用使用的相机 API、权限和厂商策略仍可能影响兼容性。
  • 用户已确认camera-direct直连版功能可用。本次同分辨率升级尚未手动验证，不能把原版成功等同于扫码识别、画面方向与稳定性已经通过。扫描App最终选择的预览或分析分辨率仍由该App和Android相机服务决定，供帧尺寸相同不强制第三方App按此尺寸分析。
  • 同分辨率协商发生在会话创建时。默认路径是固定尺寸竖屏显示，不启用flex-display。相机模式增加capture-orientation=@0保持视频为自然方向，并禁用scrcpy客户端的旋转/翻转快捷键，避免viewport变化后采集错位；普通模式保持原行为。Android运行中旋转后的预览方向仍需手动确认，未验证任意渲染适配方式。
  • 相机阶段可辅助区分：PC已发送、手机已接收、App已配置相机、相机Surface已提交首帧。没有配置相机流时，不把 PC 传输成功描述为相机输入成功。

旧方案撤回及诊断事实（2026-10-19）

out/desktop-camera-fix 中直接操作 SurfaceFlinger 的实现已撤回；不要继续使用该目录的相机模式。

第一次整窗黑屏时，只读状态确认微信已在显示79绘制：HAS_DRAWN、shown=true、isVisible=true，原显示 ON；额外镜像显示80位于默认显示组0且 OFF。手机主屏当时关闭并锁屏，原显示79没有 Keyguard。Android 的 AUTO_MIRROR 显示会被框架放回默认组，并移除不符合条件的始终解锁标志。

随后独立 SurfaceFlinger 输出使微信界面可见，但用户打开扫一扫后取景仍黑。后来读取 crash buffer 确认18:21:30发生 /system/bin/surfaceflinger 的 SIGABRT，线程 PresentAsyncTHD，错误为 Scudo ERROR: invalid chunk state when deallocating；之后图形系统重启并伴随 ADB 断开。这是实际系统崩溃，不能再将该次断开仅归因于无线网络。

现有日志不足以确定厂商 native 内存错误的具体来源，也未能独立还原崩溃前微信的相机请求。虚拟相机日志没有留下已配置流的记录，重启后的相机服务事件历史已重置，因此不能据此断言微信从未打开过相机。当前版本移除相关自定义 SF 操作，复用标准 VirtualDisplay→编码器 Surface 流程。

手动验证

  1. 确认从本次安装或完整解压目录启动，启动参数使用不指定尺寸的--new-display；相机开启时还包含--vircre-camera，且没有--display-mirror-independent或--display-id镜像分支。在“运行中 → 相机画面”确认显示手机对应的实际虚拟显示尺寸（考虑编码器像素对齐）、所选目标fps及实际接收确认fps/Mbps。
  2. 先确认微信界面正常，再手动进入扫一扫，确认相机授权、取景区域与窗口下层内容。若仍黑，在“相机画面”查看手机相机阶段并保留窗口供只读诊断。
  3. 移动、缩放、暂停和继续；把窗口拉宽后确认只映射手机内容区域。跨屏后确认两侧按桌面位置拼接，部分离屏区域补黑；最小化/锁屏后确认暂停占位，还原/解锁后确认自动恢复。手动暂停必须保持到显式继续。最后正常关闭窗口及主程序，确认能完成清理。
  4. 保持整个客户区在同一屏幕内，按住标题栏连续拖动并停留几秒不松手，确认取景跟随下层桌面变化；拖动窗口边缘时也应更新。松手后应直接保持最新画面，不补播旧帧。手动暂停后再拖动，不应绕过暂停。
  5. 普通窗口的应用缓存、图标、快捷方式、鼠标和电脑中文输入仍需分别回归。

构建与清理

pwsh -NoProfile -File tools/Build-Installer.ps1 -Version 0.1.1

构建脚本将复用的 Android shell/帧协议源码编进自定义 scrcpy-server DEX。产品运行时不额外安装 APK、不启动单独 ShellMain 进程，也不再推送独立 camera-agent jar。旧 P0 的独立构建脚本仅保留供实验使用。

关闭时先终止供帧与本工具的 scrcpy 窗口，再按 GUID 与命令行核对清理本次远端 scrcpy 服务端，删除本次 ADB forward 和 CDM 随机关联。不对微信等真实 App 执行全局 force-stop，也不删除其他窗口使用的 scrcpy-server.jar。

协议仍保留64字节VCR1头，允许有界动态尺寸：单边不超过4096、总像素不超过4096×2160，PNG(1)或JPEG(2)，单帧上限4MiB。接收端核对真实图像尺寸、MIME和本次会话约定；生产模式为与实际创建显示相同尺寸的JPEG。独立P0默认仍为640×480 PNG。运行时特性camera-display-size-v1、camera-live-move-v1，以及ready中的输入/显示尺寸和格式共同防止新旧组件混用。
